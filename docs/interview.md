## 0. 项目介绍（1 分钟版）

> 这是一个类似大众点评的本地生活后端项目，基于黑马程序员的课程完成，用 Spring Boot + Redis + MySQL 实现。主要用 Redis 解决了几类问题：用 Redis 存登录状态，用缓存工具类处理缓存穿透和击穿，用 Lua 脚本 + Redis Stream 实现异步秒杀，用 Redisson 做分布式锁。
>
> 在课程代码的基础上，我排查并修复了异步秒杀链路里的几个问题：消息确认（ACK）发错了 Stream 导致消息堆积、启动时没有创建消费者组、Redis 故障时补偿循环空转、下单时扣库存和建订单不在同一个事务里，还有我自己改 Lua 时引入的一个一人一单判断失效的 bug。

被问"项目是你自己设计的吗"：直接说是课程项目，然后把话题引到第 6 节自己修的问题上。

## 1. 登录

### Q：登录状态为什么存 Redis，不用 Session？

- Session 存在单台 Tomcat 的内存里，部署多台服务器时，请求打到另一台就拿不到登录状态
- 存 Redis 后所有服务器共享，天然支持集群

具体做法：
- 验证码：`login:code:{手机号}`，有效期 2 分钟
- 登录用户：登录成功生成随机 token，`login:token:{token}` 存一个 Hash，里面是 `UserDTO`（只有 id、昵称、头像，不含手机号、密码等敏感字段）
- 前端把 token 放在请求头 `authorization` 里

追问"为什么用 Hash 不用 String 存 JSON"：Hash 可以单独修改某个字段，而且不需要存 JSON 的引号、括号，占用更小。

### Q：为什么要两个拦截器？

| 拦截器 | 拦截范围 | 做什么 |
|---|---|---|
| `RefreshTokenInterceptor`（order 0） | 所有路径 | 有 token 就从 Redis 取出用户放进 ThreadLocal，并刷新有效期；**不管有没有登录都放行** |
| `LoginInterceptor`（order 1） | 需要登录的路径 | 只检查 ThreadLocal 里有没有用户，没有就返回 401 |

如果只有一个拦截器、只拦需要登录的路径：用户一直在浏览商铺这些不需要登录的页面，token 的有效期就不会刷新，用着用着突然掉线。

### Q：ThreadLocal 为什么要在 `afterCompletion` 里 remove？

Tomcat 用线程池，线程会被下一个请求复用。不清理的话，下一个请求可能拿到上一个用户的信息，而且会造成内存泄漏。

⚠️ 代码里 `LOGIN_USER_TTL` 是 36000 分钟，这是开发时为了方便设的，正式环境应该是 30 分钟左右。被问到就这么说。

## 2. 缓存

### Q：缓存和数据库怎么保持一致？

用的是 **Cache Aside**（旁路缓存）：

- **读**：先查缓存，没有再查数据库，查到后写入缓存并设置过期时间
- **写**：**先更新数据库，再删除缓存**（`ShopServiceImpl.update`，加了 `@Transactional`）

追问一：为什么是删缓存，不是更新缓存？
- 写多读少时，每次更新缓存都是无用功
- 并发写时，两次更新缓存的先后顺序可能和更新数据库的顺序相反，导致缓存是旧值

追问二：为什么先更新数据库，再删缓存？
- 如果先删缓存：删完后、数据库还没更新时，另一个请求读缓存没命中，从数据库读到旧值又写回缓存，缓存会一直是旧的
- 先更新数据库也有极小概率不一致（要求读请求在缓存刚好过期时读到旧值，并且比写请求更晚写入缓存），而且有过期时间兜底

追问三：要求更强的一致性怎么办？（项目里没做，知道思路即可）
- 延迟双删：更新数据库后删一次，过一会儿再删一次
- 订阅数据库的 binlog（如 Canal），由它负责删缓存，业务代码不用管

### Q：缓存穿透、击穿、雪崩分别是什么，怎么解决？

| 问题 | 是什么 | 项目里怎么做 | 其他方案 |
|---|---|---|---|
| 穿透 | 查一个**根本不存在**的数据，缓存永远不命中，请求全打到数据库 | 数据库查不到时，往缓存写一个空字符串，有效期 2 分钟（`queryWithPassThrough`） | 布隆过滤器；校验 id 格式 |
| 击穿 | 一个**热点 key 过期**，并且重建缓存比较慢，大量请求同时打到数据库 | 互斥锁（`queryWithMutex`）或逻辑过期（`queryWithLogicalExpire`） | — |
| 雪崩 | **大量 key 同时过期**，或者 Redis 宕机 | 项目里没做 | 过期时间加随机值；Redis 集群、哨兵；限流降级；多级缓存 |

缓存空值的缺点：占内存（所以有效期设短）；数据库后来插入了这条数据，短时间内读到的还是空。

### Q：互斥锁和逻辑过期怎么选？

| | 互斥锁 | 逻辑过期 |
|---|---|---|
| 做法 | 缓存没命中时用 `SETNX lock:shop:{id}` 抢锁，抢到的查数据库重建缓存，没抢到的等 50ms 再查 | key 不设过期时间，把过期时间存在值里；发现过期了就抢锁，抢到的**另开线程**重建缓存，所有请求先返回旧数据 |
| 一致性 | 好，拿到的都是新数据 | 差，重建完成前返回旧数据 |
| 性能 | 等锁的线程会阻塞 | 不阻塞 |
| 选哪个 | 对一致性要求高 | 对可用性要求高 |

⚠️ 逻辑过期要求**提前把热点数据放进缓存**（缓存预热），因为缓存没命中时它直接返回 null。

⚠️ 现在 `ShopServiceImpl.queryById` 实际用的是防穿透版本，互斥锁和逻辑过期在 `CacheClient` 里实现了，切换只要改一行。被问"你实际用的是哪个"就照实说。

⚠️ 互斥锁版本没抢到锁时是**递归调用**自己重试，并发很高时有栈溢出的风险，改成循环更好。

## 3. 全局唯一 ID

### Q：订单 ID 为什么不用数据库自增？

- 自增 ID 规律太明显，别人能猜出你一天有多少订单
- 以后分库分表时，每张表各自自增会重复

### Q：`RedisIdWorker` 是怎么生成 ID 的？

64 位 long：**高位是时间戳，低 32 位是序列号**。

- 时间戳：当前秒数减去一个起始时间（2022-01-01），左移 32 位
- 序列号：Redis 自增，key 按天分开（`icr:order:2026:11:07`），既方便按天统计订单量，也避免一个 key 无限增长
- 一天最多 2³² 个 ID，够用

追问"和雪花算法比"：雪花算法依赖机器时钟，时钟回拨会出问题，还要给每台机器分配编号；这个方案依赖 Redis，但不用管机器编号。

## 4. 秒杀（重点）

### Q：整个秒杀流程是怎样的？

```
用户请求
  └─ 执行 seckill.lua（在 Redis 里原子执行）
       ├─ 库存不足 → 返回 1
       ├─ 用户已下过单（SISMEMBER seckill:order:{券id} 用户id）→ 返回 2
       └─ 有资格：扣 Redis 库存、记录用户、XADD 消息到 seckill:stream → 返回 0
  └─ 返回 0 就直接把订单 id 返回给用户（这时数据库里还没有订单）

后台线程（单线程）
  └─ XREADGROUP 从 Stream 读消息
       └─ 加 Redisson 锁 → 事务里：检查一人一单、扣数据库库存、插入订单 → 提交 → 释放锁
       └─ XACK 确认消息
  └─ 出错时：消息不确认，留在 pending-list，从 pending-list 重新处理
```

### Q：为什么要做成异步？

原来是同步的：查券、判断时间、判断库存、加锁、查订单、扣库存、建订单，一个请求要访问好几次数据库，慢，而且所有压力都在数据库上。

改成异步后，请求里只执行一次 Lua 脚本，几毫秒就返回；写数据库的工作交给后台线程慢慢做，数据库压力被削平。

代价：
- 用户看到"抢购成功"时，数据库里还没有订单（最终一致）
- Redis 和数据库各有一份库存，要保证两边一致

### Q：怎么防止超卖？

数据库扣库存时用**乐观锁**：

```sql
update tb_seckill_voucher set stock = stock - 1 where voucher_id = ? and stock > 0
```

追问"为什么条件是 `stock > 0`，不是 `stock = 查到的值`"：后者是标准的 CAS，但并发时大量请求会因为值变了而失败，明明还有库存却抢不到；只判断 `stock > 0` 就够了。

另外，异步版本里 Redis 的 Lua 脚本已经先判断过一次库存，数据库这层是兜底。

### Q：为什么用 Lua 脚本？

判断库存、判断是否下过单、扣库存、记录用户、发消息这几步必须**一起完成**，中间不能被别的请求插进来，否则会出现两个请求都判断"还有 1 件"、都扣成功。

Redis 执行 Lua 脚本时不会执行其他命令，所以整个脚本是原子的，还能少几次网络往返。

⚠️ 追问"Lua 脚本出错会回滚吗"：不会。脚本执行到一半报错，前面已经执行的命令不会撤销。所以脚本里先做完所有判断，最后才写数据。

### Q：一人一单为什么还要加锁？

"查一下有没有订单 → 没有就插入"是两步操作。同一个用户同时发两个请求，两个都查到 0，就都插入了。

- 单机：`synchronized(userId.toString().intern())`
- 多台服务器：synchronized 只能锁住本机，需要分布式锁 → Redisson

异步版本里 Lua 脚本已经在 Redis 层挡住了重复下单，数据库层加锁 + 查订单是兜底。

### Q：为什么从阻塞队列换成 Redis Stream？

课程先用的是 JVM 里的 `BlockingQueue`，有两个问题：
- 占 JVM 内存，订单太多会撑爆
- 服务重启或宕机，队列里的订单就丢了

| 方案 | 持久化 | 消费确认 | 问题 |
|---|---|---|---|
| BlockingQueue | 无 | 无 | 上面两个 |
| Redis List（BRPOP） | 有 | 无 | 取出后处理失败，消息就丢了 |
| Redis Pub/Sub | 无 | 无 | 消费者不在线时消息直接丢 |
| **Redis Stream** | 有 | 有（消费者组 + ACK + pending-list） | 见下一题 |

### Q：Redis Stream 和 RocketMQ、Kafka 比有什么不足？

- 消息可靠性依赖 Redis 的持久化（AOF），Redis 宕机可能丢消息
- 没有死信队列、事务消息、延迟消息等功能
- 消息堆积能力受 Redis 内存限制

所以中小规模可以用 Stream，正式的大流量场景应该换专业 MQ。

### Q：消息会不会被重复消费？怎么保证幂等？

会。比如订单已经插入数据库了，但发 ACK 前服务挂了，消息留在 pending-list，重启后会再处理一次。

项目里靠"加锁 + 先查有没有订单"保证不会重复建单。⚠️ 更可靠的做法是给 `tb_voucher_order` 的 `(user_id, voucher_id)` 加**唯一索引**，现在表里只有主键索引，这是可以改进的点。

### Q：只有一个消费者线程，处理不过来怎么办？

现在是一个线程、消费者名写死为 `c1`。可以：
- 每台服务器用不同的消费者名加入同一个消费者组，Stream 会把消息分给不同的消费者
- 单机内开多个线程消费

## 5. 分布式锁

### Q：自己用 SETNX 实现的锁有什么问题，怎么一步步改进的？

1. **基础版**：`SET lock:order:{userId} 值 NX EX 10`。必须带过期时间，否则拿到锁的服务挂了，锁永远不释放
2. **误删别人的锁**：线程 A 业务太慢，锁过期了；线程 B 拿到锁；A 执行完把 B 的锁删了。
   改进：锁的值存 `UUID + 线程 id`，删除前先判断是不是自己的
3. **判断和删除不是原子的**：A 判断完"是我的锁"之后发生了卡顿（比如 GC），这期间锁过期、B 拿到锁，A 恢复后照样删掉了 B 的锁。
   改进：判断和删除放进 Lua 脚本（`unlock.lua`）
4. **还剩下的问题**：不可重入；获取失败不会重试；业务没执行完锁就过期；Redis 主从切换时锁可能丢失 → 用 **Redisson**

### Q：Redisson 解决了哪些问题，原理是什么？

| 问题 | Redisson 怎么做 |
|---|---|
| 可重入 | 锁用 Hash 存：field 是"客户端 id + 线程 id"，value 是重入次数，加锁 +1、释放 -1，减到 0 才删除。全部用 Lua 脚本保证原子 |
| 重试 | `tryLock(等待时间)`：获取失败后订阅锁释放的消息，收到通知再重试，不是一直空转 |
| 锁过期但业务没做完 | **看门狗**：没有指定过期时间时，默认 30 秒，每 10 秒自动续期到 30 秒。服务挂了就不再续期，锁会自然过期，不会死锁 |
| 主从切换丢锁 | MultiLock：向多个独立的 Redis 节点都加锁，全部成功才算成功 |

项目里用的是 `lock.tryLock()`（不等待、不指定过期时间），所以看门狗是开启的。

## 6. 我做的改进（重点）

这一节最能体现自己的能力，每个问题都要能讲清楚：**怎么发现的 → 原因是什么 → 怎么改的**。

### ① ACK 发错了 Stream

- **现象**：原版从 `stream.orders` 读消息，确认时却写成了 `XACK s1 g1 id`。`XACK` 对不存在的 key 不报错、只返回 0，所以表面上一切正常，实际上消息从来没被确认，pending-list 越来越长
- **怎么查**：用 `XPENDING` 看 pending-list 的长度
- **怎么改**：Stream 名、组名、消费者名统一成常量，读和确认都用同一个；读消息封装成一个 `readOrders` 方法

### ② 启动时没有创建消费者组

- **现象**：原版要手动在 redis-cli 执行 `XGROUP CREATE`，否则第一次读取报 `NOGROUP`
- **怎么改**：在 `@PostConstruct` 里执行 `XGROUP CREATE seckill:stream g1 0 MKSTREAM`。`MKSTREAM` 让 Stream 不存在时自动创建；组已存在时会报 `BUSYGROUP`，捕获后忽略

### ③ Redis 故障时补偿循环空转

- **现象**：原版处理 pending-list 出错后马上进入下一轮，Redis 一旦连不上，就变成没有任何等待的死循环，CPU 占满、日志刷屏
- **怎么改**：出错后等 1 秒再继续，并且退出补偿循环、回到主循环；循环条件从 `while(true)` 改成检查线程中断状态

### ④ 异步下单不在事务里

- **现象**：扣数据库库存和插入订单是两条独立的 SQL。如果库存扣了、插入失败，库存就白扣了；而且消息没被确认，补偿时会再扣一次
- **为什么不直接加 `@Transactional`**：`@Transactional` 靠 Spring 生成的代理对象生效，类内部用 `this` 调用自己的方法不经过代理，注解不起作用。后台线程调用的正是同一个类里的方法
- **怎么改**：注入 `TransactionTemplate`，用 `executeWithoutResult` 把两步包进一个事务
- **锁放在事务外面**：先提交事务、再释放锁。如果反过来，锁释放后、事务提交前，另一个线程拿到锁查订单，查到的还是 0（未提交的数据看不到），就会重复下单

追问"`@Transactional` 还有哪些失效的情况"：
- 方法不是 public
- 类内部自己调用（上面这种）
- 异常被 catch 住没有抛出
- 抛出的是受检异常，默认只对 RuntimeException 和 Error 回滚，需要 `rollbackFor`
- 在另一个线程里执行（事务和线程绑定）
- 类没有交给 Spring 管理

### ⑤ 自己改 Lua 时引入的 bug（可以当成调试经历讲）

- **现象**：我改 `seckill.lua` 时把一人一单的判断写成了 `SISMEMBER orderKey orderId`，而存进去的是 `userId`。订单 id 每次都是新生成的，所以永远判断"没下过单"，Redis 这层的一人一单完全失效
- **后果**：数据库层的检查会挡住重复订单，但 Redis 库存已经扣了，用户还看到"抢购成功"
- **怎么发现的**：整理代码准备上传 GitHub 时，和课程原版逐行对比发现的。之后测试时也遇到了它会造成的现象：页面显示抢购成功，但库存没减，后台日志报"不允许重复下单"
- **顺便改了**：库存 key 不存在时 `tonumber(nil) <= 0` 会让脚本报错，改成按库存不足处理

### Q：测试时发现 Redis 和数据库库存对不上，是怎么回事？

这正是异步方案的一个固有问题（第 ⑤ 条测试时遇到的）：

Redis 判断有资格 → 扣了 Redis 库存 → 后台线程在数据库这层因为某种原因拒绝了（比如数据库里已经有这个用户的订单）→ 数据库库存没扣，用户却看到了成功。

改进思路：
- 数据库层拒绝时做补偿：把 Redis 库存加回去（`INCR`），把用户从 `seckill:order` 集合里移除
- 前端拿到订单 id 后轮询订单状态，而不是直接显示成功

## 7. 点赞、关注、Feed 流、附近商铺、签到

### Q：点赞为什么用 ZSet？

- `blog:liked:{笔记id}`，成员是用户 id，分数是点赞时间
- 判断是否点过赞：`ZSCORE`
- 显示最早点赞的 5 个人：`ZRANGE key 0 4`
- 用 Set 能判断是否点过赞，但没法按时间排序

### Q：共同关注怎么做？

每个用户的关注列表存一个 Set（`follows:{用户id}`），两个人的共同关注就是 `SINTER` 求交集。

### Q：Feed 流怎么实现？为什么不能用普通分页？

用的是**推模式**（写扩散）：发笔记时，把笔记 id 推到每个粉丝的收件箱 `feed:{粉丝id}`（ZSet，分数是时间戳）。

| 模式 | 做法 | 适合 |
|---|---|---|
| 拉模式 | 看的时候去拉所有关注的人的笔记再合并 | 读的时候慢 |
| 推模式 | 发的时候推给所有粉丝 | 粉丝少；大 V 有几百万粉丝时写入量太大 |
| 推拉结合 | 普通用户推，大 V 拉；或者只推给活跃粉丝 | 实际产品常用 |

**不能用下标分页**：收件箱一直有新数据进来，按下标翻页时，新数据会把旧数据往后挤，下一页会出现重复。

**滚动分页**：`ZREVRANGEBYSCORE key 上一页最小时间戳 0 LIMIT offset 2`
- 每次从上一页的最小时间戳往前查
- `offset` 是上一页里分数等于最小时间戳的条数，用来跳过时间戳相同、已经返回过的数据

### Q：附近商铺怎么查？

- 按商铺类型存 GEO：`shop:geo:{类型id}`，成员是商铺 id
- `GEOSEARCH` 按经纬度查 5 公里内、按距离排序的商铺，带上距离
- ⚠️ GEOSEARCH 只能从第 0 条取到第 N 条，没法直接跳过前面的，所以是查出 0 到 end 条后在内存里截取 from 到 end，页数越往后查的越多

### Q：签到怎么做？连续签到天数怎么算？

- **BitMap**：`sign:{用户id}:{年月}`，每月一个 key，第几天就把第几位设为 1（`SETBIT`）。一个用户一个月只要 31 位，非常省内存
- **连续签到**：`BITFIELD key GET u{今天是几号} 0` 取出本月到今天的所有位，得到一个整数；然后从最低位开始，`& 1` 判断这一天有没有签到，再右移一位，直到遇到 0

### Q：UV 统计用什么？（项目里只写了测试，了解即可）

HyperLogLog：每个 key 固定最多 12KB，误差约 0.81%，适合统计大量用户的去重数量，不需要精确值的场景。

## 8. 项目的不足和改进方向

被问"项目还有什么可以改进的"时，从这里挑两三条：

1. **Redis 和数据库库存可能不一致**：数据库层拒绝订单时，没有把 Redis 库存加回去（见第 6 节）
2. **订单表没有唯一索引**：应该给 `(user_id, voucher_id)` 加唯一索引，作为一人一单的最后防线
3. **只有一个消费者线程**：可以多实例、多消费者
4. **秒杀接口没有限流**：可以按用户或 IP 限流，挡住脚本刷接口
5. **用户看到的"成功"不是最终结果**：应该返回"排队中"，前端轮询订单状态
6. **没有做压测**：⚠️ 被问 QPS 时不要编数字，照实说没压测过，可以讲打算怎么测（JMeter，1000 个线程同时抢 100 张券，验证不超卖、一人一单）
